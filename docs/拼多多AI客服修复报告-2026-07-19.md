### 修复 1：ShopSupervisor.testReply pipeline 误报

**文件**：[src/shop/ShopSupervisor.ts](file:///d:/code/AIkefu/src/shop/ShopSupervisor.ts#L2256-L2266)

**问题**：
DeepSeekClient.chat() 在 API Key 无效/熔断时返回 `model: 'fallback'` 兜底响应（而非抛异常），导致 `runTestReply` pipeline 错误地报告 `status: 'ok'`。用户会误以为 LLM 真实可用，实际收到的是「系统繁忙，请稍后再试或联系人工客服」兜底文案。

**修复前**：
```typescript
reply = response.content;
tokenInput = response.tokenInput;
tokenOutput = response.tokenOutput;
const truncNote = response.truncated ? ', 续写后仍截断' : '';
const scenarioNote = scenario ? `, 场景=${scenario}` : '';
pipeline.push({ step: 'DeepSeek', status: 'ok', detail: `${response.model}${scenarioNote}, ${response.latencyMs}ms${truncNote}` });
```

**修复后**：
```typescript
reply = response.content;
tokenInput = response.tokenInput;
tokenOutput = response.tokenOutput;
const truncNote = response.truncated ? ', 续写后仍截断' : '';
const scenarioNote = scenario ? `, 场景=${scenario}` : '';
// 检查是否为 fallback 兜底响应（DeepSeekClient 在 API Key 无效/熔断时返回 model='fallback' 或 'circuit-open'）
// 这种情况下不应该报告 status='ok'，否则会让用户误以为 LLM 真实可用
if (response.model === 'fallback' || response.model === 'circuit-open') {
  pipeline.push({
    step: 'DeepSeek',
    status: 'fail',
    detail: `LLM 兜底返回（model=${response.model}, ${response.latencyMs}ms）— 可能 API Key 无效、熔断或余额不足`,
  });
} else {
  pipeline.push({ step: 'DeepSeek', status: 'ok', detail: `${response.model}${scenarioNote}, ${response.latencyMs}ms${truncNote}` });
}
```

**关键洞察**：DeepSeekClient 设计为「内部消化异常」返回 fallback，调用方必须主动检查 `model` 字段判断是否真实成功，try/catch 抓不到失败。

### 修复 2：WebviewClient.executeScript 不捕获渲染进程错误

**文件**：[src/cdp/WebviewClient.ts](file:///d:/code/AIkefu/src/cdp/WebviewClient.ts#L1491-L1526)

**问题**：
原实现只有一行 `return this.webContents.executeJavaScript(script)`，失败时 Electron 只返回泛化错误 `"Script failed to execute, this normally means an error was thrown"`，不暴露具体 JS 异常。导致拼多多商品同步失败时无法定位根因，日志只有泛化错误信息。

**修复前**：
```typescript
async executeScript(script: string): Promise<unknown> {
  if (!this.webContents || this.webContents.isDestroyed()) {
    throw new Error('WebContents 不可用');
  }
  return this.webContents.executeJavaScript(script);
}
```

**修复后**：
```typescript
async executeScript(script: string): Promise<unknown> {
  if (!this.webContents || this.webContents.isDestroyed()) {
    throw new Error('WebContents 不可用');
  }
  // 订阅 console-message 事件，捕获渲染进程的 console.error/warning 输出。
  // webContents.executeJavaScript 在脚本抛未捕获异常时，只返回泛化错误信息
  // "Script failed to execute, this normally means an error was thrown."
  // 不会暴露具体的 JS 异常详情。这里通过订阅 console-message 捕获详细错误，
  // 在脚本失败时附加到错误信息中以便诊断。
  const consoleErrors: string[] = [];
  const handler = (...args: unknown[]): void => {
    const level = args[1] as number;
    const message = args[2] as string;
    const line = args[3] as number;
    const sourceId = args[4] as string;
    if (level >= 2) {
      consoleErrors.push(`[L${line} ${sourceId}] ${message}`);
    }
  };
  this.webContents.on('console-message', handler);
  try {
    return await this.webContents.executeJavaScript(script);
  } catch (err) {
    const errMsg = err instanceof Error ? err.message : String(err);
    if (consoleErrors.length > 0) {
      const detail = consoleErrors.slice(0, 10).join('\n  ');
      throw new Error(`${errMsg}\n渲染进程 console 错误:\n  ${detail}`);
    }
    throw err;
  } finally {
    this.webContents.off('console-message', handler);
  }
}
```

**关键洞察**：Electron webContents.executeJavaScript 的错误信息是泛化的；要拿到具体异常必须监听 `console-message` 事件（事件签名 `(event, level, message, line, sourceId)`，level 0=verbose/1=info/2=warning/3=error）。

**已知副作用**：Electron 输出 deprecation 警告 `(electron) 'console-message' arguments are deprecated`——不影响功能，未来升级 Electron 时需要改 handler 签名为 `Event<WebContentsConsoleMessageEventParams>`。

### 修复 3：ProductSyncService.buildScrapeScript 缺少外层 try 块

**文件**：[src/product/ProductSyncService.ts](file:///d:/code/AIkefu/src/product/ProductSyncService.ts#L2020-L2022)

**问题**：
`buildScrapeScript` 生成的 ~450 行 async IIFE 抓取脚本中，L2169 有 `catch(scriptErr) {` 但**没有对应的外层 `try {` 块**。导致 `SyntaxError: Unexpected token 'catch'` 在脚本 parse 阶段就抛出（连 try/catch 内部都没执行）。这破坏了所有非 feige 平台（pinduoduo/kuaishou/weixin）的商品同步，每次返回：
```
errors: 1, total: 0
- Script failed to execute, this normally means an error was thrown.
```

**修复**（在「步骤2：点击商品标签页」前加外层 try 块）：
```typescript
debug.steps.push({ step: 'record_active_tab', activeTab: activeTabText });

// 外层 try 包裹所有抓取步骤（步骤2/3/4），任何未捕获的异常都会被 L2169 的 catch(scriptErr) 捕获
// 缺少这个 try 会导致 L2169 的 catch 没有对应的 try，引发 SyntaxError: Unexpected token 'catch'
try {

// ===== 步骤2：点击"商品"标签页，抓取商品面板 =====
try {
  ...
```

**验证**：修复后拼多多商品同步成功 `total: 5, imported: 5, errors: 0`（耗时 7 秒）。

**关键洞察**：修复顺序依赖 — 必须先应用「修复 2」才能在错误信息中看到真正的 `SyntaxError: Unexpected token 'catch'`，再据此定位到 `buildScrapeScript` 模板字符串的结构错误。

### 修复 5：WebviewClient 测试 mock 缺 .off() 方法

**文件**：[tests/unit/cdp/WebviewClient.test.ts](file:///d:/code/AIkefu/tests/unit/cdp/WebviewClient.test.ts#L17-L29)

**问题**：
修复 2 给 executeScript 加了 `webContents.off('console-message', handler)`，但测试 mock 只有 `on: jest.fn()` 没有 `off`，导致回归：
```
FAIL tests/unit/cdp/WebviewClient.test.ts
  ● WebviewClient › executeScript › 正常执行脚本
    TypeError: this.webContents.off is not a function
```

**修复**：在 mock 对象中补 `off: jest.fn()`：
```typescript
webContents = {
  executeJavaScript: jest.fn().mockResolvedValue(undefined),
  sendInputEvent: jest.fn().mockResolvedValue(undefined),
  isDestroyed: jest.fn().mockReturnValue(false),
  isCrashed: jest.fn().mockReturnValue(false),
  reload: jest.fn().mockResolvedValue(undefined),
  on: jest.fn(),
  // executeScript 在脚本失败时需要 .off('console-message', handler) 解除订阅，
  // 测试 mock 需提供 .off 方法（与 .on 对称），否则 finally 块会抛 "off is not a function"
  off: jest.fn(),
  id: 1,
  session: {} as any,
};
```

**教训**：修改生产代码使用新接口方法时，必须同步检查测试 mock 是否实现了该方法（`IWebContents` 接口在 `src/cdp/types.ts` L42-51 同时声明了 `on` 和 `off`）。

**文件**：[tests/unit/intent/LlmIntentRecognizer.test.ts](file:///d:/code/AIkefu/tests/unit/intent/LlmIntentRecognizer.test.ts)（全文重写）

**问题**：
源码 `src/intent/LlmIntentRecognizer.ts` 已重构从 `DeepSeekClient.chat()` 改为 `ModelGateway.route()`（让 DeepSeek 故障时能 fallback 到 tier2/tier3 其他 provider），但测试仍 mock 旧的 `mockClient.chat`。被测代码调用 `gateway.route()` 返回 undefined，try/catch 兜底返回 `unknown`/0，4 个测试失败：

FAIL tests/unit/intent/LlmIntentRecognizer.test.ts
  ● LlmIntentRecognizer › 解析有效 JSON 返回增强意图     (期望 "product_inquiry"，收到 "unknown")
  ● LlmIntentRecognizer › 缺少 emotion 字段时默认 neutral (期望 "greeting"，收到 "unknown")

**修复**：全文重写测试，所有 `mockClient.chat` 替换为 `mockGateway.route`，响应类型从 `ChatResponse` 改为 `GatewayResponse`（增加 `confidence/provider/costYuan` 字段），新增断言 `callArg.cascade === false` 和 `callArg.preferredTier === 'tier2'` 验证轻量调用走 directRoute。

**关键洞察**：源码重构时若接口变化，测试必须同步更新 — 不然单测看起来在测试新行为，实际 mock 的是旧接口，被测代码完全没执行到，因 try/catch 兜底反而都返回默认值"通过"，掩盖真实问题。

## 四、⚠️ 用户待办事项（无法自动修复）

### DeepSeek API Key 需重新输入

**当前状态**：DeepSeek API Key 仍是 Phase 5 F5 测试时写入的测试值 `sk-pha****6191`（非真实 key）。

**原因**：Phase 5 多 provider 验证脚本 F5 用 `updateLlmApiKey('deepseek', testKey)` 测试写入逻辑，覆盖了用户原 API Key。DPAPI 加密存储无法读取明文，**无法自动恢复**。

**影响**：
- 拼多多 AI 自动回复将使用「兜底文案」（"抱歉，系统繁忙，请稍后再试或联系人工客服"）而非真实 LLM 生成回复
- testReply 现在会正确报告 `DeepSeek: fail`（修复 1 的成果），用户可清晰看到 LLM 不可用

**操作步骤**：
1. 启动应用：`npm run electron:start`
2. 进入「设置」→「AI 模型」
3. 在 DeepSeek 行输入真实 API Key（从 https://platform.deepseek.com/api_keys 获取）
4. 保存后即可立即生效（无需重启）
