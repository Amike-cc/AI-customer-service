## 三、严重 BUG（16 个）

### 🔴 安全类（3 个）

#### S-1. 原生模态窗口 XSS → RCE（最高危）
- **位置**：`electron/native-modal.ts:152-156, 68, 76`
- **问题**：Modal 窗口 `webPreferences` 为 `nodeIntegration:true, contextIsolation:false, sandbox:false`，且 `modal:init` 里用 `innerHTML = data.content / data.footerHtml`。`modal:open` 主处理器（`ipc-handlers.ts:309`）对 content/footerHtml **不做任何校验或转义**。渲染层任何可控字符串（店铺名、模板内容、用户输入）注入 `<img onerror=...>` 即可在拥有 Node 全权限的上下文执行代码，等同 RCE。
- **修复**：Modal 窗口改为 `contextIsolation:true, nodeIntegration:false, sandbox:true` + preload 白名单；文本内容一律 `textContent`；footerHtml 必须保留 HTML 时引入 DOMPurify 消毒。

#### S-2. `debug:executeScript` 任意 JS 注入
- **位置**：`electron/ipc-handlers.ts:436` + `electron/preload.ts:578-582`
- **问题**：preload 暴露 `shop.executeDebugScript`，主进程仅校验字符串长度（≤50000），随后通过 `supervisor.executeScriptOnShop` 在**已登录店铺 webview 主帧**执行任意 JS。一旦渲染进程被攻陷（配合 S-1 或任何渲染层漏洞），攻击者可读取平台 cookie/localStorage、劫持会话、以店铺身份调用平台 API。
- **修复**：`NODE_ENV=production` 下移除 `debug:*` 系列 IPC 注册与 preload 暴露；或加入主进程签名校验。

#### S-3. WebContentsView 关闭 contextIsolation，指纹伪装可被探测
- **位置**：`electron/webview-manager.ts:129`
- **问题**：店铺 webview `contextIsolation:false`，第三方平台页面（飞鸽/拼多多等）与 preload 注入脚本共享 JS 全局。页面 JS 可读取/篡改 preload 写入的 `__FINGERPRINT_DATA__` 等 window 属性，**指纹伪装可被平台侧脚本探测并绕过**，直接导致封号风险。
- **修复**：改为 `contextIsolation:true`；指纹注入走 `ses.registerPreloadScript({type:'frame'})` 的 isolated world。

### 🔴 核心链路失效（4 个）

#### S-4. ModelGateway 级联降级完全失效
- **位置**：`src/gateway/providers/DeepSeekProvider.ts:41-59` + `src/deepseek/DeepSeekClient.ts:212-258` + `src/gateway/ConfidenceEvaluator.ts`
- **问题**：`DeepSeekClient.chat()` 吞掉所有异常返回 fallback 文案，永不抛错 → `ModelGateway.cascade()` 的 try/catch 永远捕获不到失败。更糟的是，fallback 文案（"亲，请稍后再试"之类）经 `ConfidenceEvaluator` 打分约 **0.83**（有句号、长度适中、无不确定词），高于典型阈值 0.75，cascade 直接 break，把兜底客套话当正常回复发给买家。**Qwen/OpenAI/Claude 级联形同虚设**。
- **修复**：fallback 时设 `model='fallback'` 标记，ConfidenceEvaluator 检测到此标记直接给 0 分；或 DeepSeekProvider 检测 `model==='fallback'` 时主动 throw。

#### S-5. SessionAnalyzer 从未真正运行
- **位置**：`src/analytics/SessionAnalyzer.ts:116-120`
- **问题**：
```ts
private getActiveShops(): string[] {
  return Array.from(new Set(this.repo.getBehaviorCounts('', 0).map(() => 'all')));
}
```
返回常量 `['all']` 作为 shopId，后续 `getActiveSessions('all', …)` 查不到任何记录。**整个会话分析功能自始至终端不到数据**。
- **修复**：从 repo 查询 `SELECT DISTINCT shop_id`。

#### S-6. CdpClient 断开后无法重连
- **位置**：`src/cdp/CdpClient.ts:144-178, 180-203`
- **问题**：`disconnect()` 设 `stopped=true`，但 `connect()` **没有重置 `stopped=false`**。`scheduleNextPoll` / `scheduleNextUnreadScan` 都检查 `if (this.stopped) return`。一旦断开重连，轮询和扫描器永远不会启动，只剩 Observer 注入——消息通道实际已死。
- **修复**：`connect()` 入口加 `this.stopped = false;`（一行修复，功能致命）。

#### S-7. `agent:assign` IPC 通道名对不上
- **位置**：`electron/preload.ts:924-925` vs `electron/ipc-handlers.ts`（未注册）
- **问题**：preload 暴露 `agent.assign → invoke('agent:assign')`，但主进程没有对应 handler。渲染层 `AgentPanel.tsx` 调用时抛 `No handler registered for 'agent:assign'`。**人工坐席分配功能完全不可用**。
- **修复**：在 ipc-handlers.ts 补注册，或从 preload/renderer 移除该 API。

### 🔴 资源泄漏与竞态（6 个）

#### S-8. VisionClient.stop() 不 kill Python 子进程
- **位置**：`src/vision/VisionClient.ts:126-134`（已复核确认）
- **问题**：`stop()` 只 `stdin.end()` + `proc=null`，**没有 `proc.kill()`**。Python 子进程若因 OCR 死循环/模型加载卡死不退出，主进程再次 `start()` 会 spawn 第二个 Python 进程（每个 800MB+ 内存）。多店铺 7×24 挂机下累积 OOM。
- **修复**：`stop()` 中 `this.proc?.kill('SIGTERM')`，500ms 后 `SIGKILL` 兜底。

#### S-9. ShopInstance 恢复流程未清理旧 WebContents 监听器 → 恢复风暴
- **位置**：`src/shop/ShopInstance.ts:586-624`
- **问题**：`attemptRecovery` 中旧 `webContents` 被 `removeView` 但未 `off` 旧监听器（`did-finish-load`/`crashed`/`destroyed`/`render-process-gone`），`registerCrashHandler(newWebContents)` 直接覆盖 `crashHandlerRefs`。旧 WebContents 上仍挂原 handler（闭包引用旧 this），若旧 WebContents 未立即销毁，崩溃时再次触发 `handleWebviewCrash`，引发**恢复风暴**。
- **修复**：`attemptRecovery` 开头先 `off` 所有旧 handler 再 `removeView`。

#### S-10. handleWebviewCrash 竞态 — 最大恢复次数被提前耗尽
- **位置**：`src/shop/ShopInstance.ts:551-584`
- **问题**：`crashed`/`destroyed`/`render-process-gone` 三个事件可在一次崩溃中连续同步触发。第一个 handler 的 `setTimeout` 同步赋值在尾部，第二三个 handler 已通过 `if (this.recoveryTimer) return` 检查，`recoveryAttempts` 被加 3 次但实际只调度 1 次（后两次 setTimeout 覆盖前者）。
- **修复**：handler 入口立即设置占位标志 `this.recoveryTimer = PLACEHOLDER`，再算 delay。

#### S-11. MetricsCollector.flush 失败导致指标永久丢失 + 可能进程崩溃
- **位置**：`src/monitor/MetricsCollector.ts:54-127`
- **问题**：`flush()` 先 `clear()` 三个 map 再执行 SQL 事务。INSERT 抛错（磁盘满/锁库）时 ROLLBACK，但内存数据已清空，**这批指标彻底丢失**。catch 中的 `ROLLBACK` 自身若也抛错（BEGIN 失败时无事务可回滚）将产生未捕获异常导致进程崩溃。
- **修复**：事务成功后再 clear；失败回灌；ROLLBACK 用 try/catch 包裹；改用 `db.transaction()`。

#### S-12. ShopStateMachine Degrading 超时与异步回调竞态 → 视觉资源泄漏
- **位置**：`src/state/ShopStateMachine.ts:216-226`
- **问题**：`startDegrading` 同时设置 `degrading_timeout` 定时器（5s 后转 Error）和 `onEnterDegrading()` 异步回调。若回调在 5s 后 resolve，超时已把状态转为 Error，回调内初始化的视觉流资源在 Error 态下**没有清理路径**。
- **修复**：先 await onEnterDegrading 再启动超时；或回调 resolve 后先取消超时再 transition。

#### S-13. OutreachExecutor 失败路径占用 outreachInProgress 标志 3 秒丢真实消息
- **位置**：`src/outreach/OutreachExecutor.ts:54-65`
- **问题**：`finally` 统一 `setTimeout(3000)` 后清除标志。若 `switchToSession` 抛错立即失败，3 秒内真实买家消息会被 ShopSupervisor 当触达消息丢弃。挂机场景下持续丢消息。
- **修复**：成功路径延迟清除，失败路径立即清除。

### 🔴 数据正确性（3 个）

#### S-14. AuditRepo 审计链哈希取"上一条"不稳定 → 整链校验失效
- **位置**：`src/db/repos/AuditRepo.ts:40-46`
- **问题**：`ORDER BY created_at DESC LIMIT 1` 在多条记录同毫秒时返回行不确定（SQLite 不保证稳定次序），`prevHash` 取错导致后续整条链与 verifyChain 对不上。同毫秒写入两条回复在高并发下完全可能。
- **修复**：`ORDER BY created_at DESC, id DESC LIMIT 1`，或 `MAX(id)`。

#### S-15. BudgetTracker 跨日预算检查漏判 → 白天预算被错误拒单
- **位置**：`src/scheduler/BudgetTracker.ts:38-58`
- **问题**：`checkDayRollover()` 只在 `record()` 与 `getGlobalDailyCost()` 中调用。`isShopOverBudget()`/`isGlobalOverBudget()`/`getDailyCost()` 直接读 `dailyCost` 未触发 rollover。**跨日 0 点后若无新 record，预算检查仍用昨日累计成本**，直接拒单。
- **修复**：三个查询入口先调 `checkDayRollover()`。

#### S-16. backend.ts 启动 5s 后备份与 shutdown 竞态
- **位置**：`src/backend.ts:146-149`
- **问题**：`setTimeout(...,5000)` 触发 `db.backup()`，但 `shutdown()` 不等待备份完成就先 `db.close()`。better-sqlite3 在已 close 连接上 backup 行为未定义。timeoutId 未保存也无法取消。
- **修复**：保存 timeoutId，shutdown 时 clearTimeout；维护 pending Promise 列表，shutdown 时 `Promise.allSettled` 后再 close db。
